# RDP Security Suite

Защита Windows-сервера от подбора паролей по RDP: слежение за неудачными входами, автоматическая блокировка атакующих IP через штатный Windows Firewall, GUI-панель управления и удалённое управление через Telegram-бота.

Состоит из двух частей:

- **WinService** (`RDPSecurityService`) — Windows-служба, которая делает всю работу: детектирует атаки, ведёт логи, применяет блокировки, обслуживает Telegram-бота.
- **RDPMonitor** — GUI-приложение (WinForms) для настройки службы, просмотра логов и ручного управления блокировками/whitelist.

## Как это работает

### Детектирование

Служба подписывается на события Windows Security Event Log в реальном времени:

- **4625** (неудачный вход) — основной триггер. IP атакующего извлекается из события и проверяется по нескольким эвристикам ниже.
- **4624/4634/4647** (успешный вход/выход) — используется, чтобы не считать опечатку уже залогиненного пользователя атакой (например, при разблокировке экрана).

Порт RDP берётся из конфига (`port`), а не захардкожен — можно вынести RDP на нестандартный порт (например, 55900), это не сломает ни детекцию, ни блокировку.

### Эвристики анти-брута

Все они работают параллельно, независимо друг от друга, и при срабатывании нескольких одновременно применяется самая строгая блокировка:

| Эвристика | Что ловит | Настройка |
|---|---|---|
| **Per-IP порог** | N неудачных попыток с одного IP за последние `failedAttemptsWindowDays` дней (по умолчанию 1) — многоуровневая эскалация (3 → 30 мин, 5 → 3 ч, 7 → 2 суток) | `levels`, `failedAttemptsWindowDays` |
| **Spray** | Один и тот же логин атакуют с N разных IP по всему интернету за короткое окно | `antiBrute.spray` |
| **Subnet+user spray** | Тот же логин атакуют с N разных IP **внутри одной /24-подсети** — ловит «low-and-slow» перебор (1-2 попытки на IP), который не поймать по одному per-IP порогу | `antiBrute.subnetUserSpray` |
| **IP abuse** | С одного IP перебирают N разных логинов | `antiBrute.ipAbuse` |
| **Subnet-эскалация** | Если из одной /24 уже забанено N разных IP — банится вся подсеть (с проверкой, что там нет активной легитимной RDP-сессии или whitelisted-адреса) | `antiBrute.subnet` |
| **Recurrence** | Повторные баны одного IP увеличивают время следующей блокировки | `antiBrute.recurrence` |

Локальные/приватные диапазоны (10.x, 172.16–31.x, 192.168.x, loopback) и явный whitelist (`whiteList.log`) никогда не блокируются.

Счётчик попыток и активные баны корректно обнуляются как при истечении срока, так и при ручном разбане (из Monitor или Telegram) — включая случай, когда несколько разных сотрудников сидят за одним «серым» IP офиса и иногда опечатываются в пароле.

### Применение блокировки

Реальная блокировка — через 16 правил Windows Firewall (`RDP_BLOCK_0` … `RDP_BLOCK_15`, шардинг по IP), а не одно гигантское правило: так обновление одного бана не требует переписывать список из тысяч чужих адресов и не может «уронить» синхронизацию для всех остальных. Источник истины — файл `block_list.log`; служба перечитывает его при любом изменении и раз в 15 минут принудительно сверяет фактическое состояние firewall с этим файлом (самовосстановление после ручного вмешательства извне).

### Telegram-бот

Встроенный бот (long polling, без вебхуков) с двумя ролями:

- **admin** — полный доступ: статусы, ручной бан/разбан, остановка службы/монитора, управление whitelist.
- **limited** — только кнопка «Розблокуй мене» (self-unban заранее сконфигурированного IP, `telegram.selfUnbanIp`), для непривилегированных пользователей.

Ключевые команды: `/status`, `/status all`, `/thresholds`, `/ban <ip> <длительность>`, `/unban <ip>`, `/service start|stop|status`, `/monitor start|stop`, `/here` (геолокация через HTTP-пробник).

## Установка

Актуальный путь установки — из готового релиз-пакета:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
cd .\release\RDP-Security-Suite-ZIP
.\install-clean.ps1 -StartMonitor
```

Подробности и чек-лист проверки — в [CANONICAL_INSTALL.md](CANONICAL_INSTALL.md).

Monitor требует запуска с правами администратора (это прописано в его манифесте) — без этого он не сможет читать/писать конфигурацию и логи службы.

## Настройка

Конфигурация лежит в `C:\ProgramData\RDPSecurityService\config.json`. Файл хранится **зашифрованным** (Windows DPAPI, machine-scope) — вручную его не редактируют, все изменения делаются через Monitor (вкладка Settings/Telegram) или через Telegram-команды администратора. Схема полей — в [`WinService/config.example.json`](WinService/config.example.json) (этот файл — просто справочный шаблон в открытом виде, не то, что реально читает служба).

Основные поля:

- `port` — порт RDP, который слушает служба для корреляции с событиями входа.
- `failedAttemptsWindowDays` — сколько дней «живёт» одна неудачная попытка в per-IP счётчике.
- `levels` — пороги эскалации блокировки (попытки → минуты бана).
- `telegram` — токен бота, ID чата администратора, список разрешённых телефонов для limited-роли, `selfUnbanIp`.
- `antiBrute` — включение и параметры каждой из эвристик выше.

## Ограничения

Это дополнительный слой защиты поверх штатной гигиены, а не замена ей:

- Не заменяет NLA, сложные пароли, MFA — угадывание пароля за 1 попытку никакой порог не остановит.
- Не защищает от атак из приватных/локальных диапазонов IP (by design) — нулевая защита от бокового перемещения внутри сети.
- Атака с одновременной ротацией и IP, и логина на каждую попытку (редкий, целевой сценарий) обходит все текущие эвристики.

Рекомендуемая практика: RDP за VPN, NLA включена, порт вынесен с 3389 — этот сервис как дополнительный рубеж против массового автоматического сканирования и скриптового брутфорса.
