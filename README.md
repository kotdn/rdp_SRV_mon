# RDP Security Suite

Захист Windows-сервера від підбору паролів по RDP: стеження за невдалими входами, автоматичне блокування атакуючих IP через штатний Windows Firewall, GUI-панель керування та віддалене керування через Telegram-бота.

Складається з двох частин:

- **WinService** (`RDPSecurityService`) — Windows-служба, яка робить усю роботу: детектує атаки, веде логи, застосовує блокування, обслуговує Telegram-бота.
- **RDPMonitor** — GUI-застосунок (WinForms) для налаштування служби, перегляду логів і ручного керування блокуваннями/whitelist.

## Як це працює

### Детектування

Служба підписується на події Windows Security Event Log у реальному часі:

- **4625** (невдалий вхід) — основний тригер. IP атакуючого витягується з події та перевіряється за кількома евристиками нижче.
- **4624/4634/4647** (успішний вхід/вихід) — використовується, щоб не вважати описку вже залогіненого користувача атакою (наприклад, при розблокуванні екрана).

Порт RDP береться з конфігу (`port`), а не захардкоджений — можна винести RDP на нестандартний порт (наприклад, 55900), це не зламає ні детекцію, ні блокування.

### Евристики анти-брута

Усі вони працюють паралельно, незалежно одна від одної, і при спрацюванні кількох одночасно застосовується найсуворіше блокування:

| Евристика | Що ловить | Налаштування |
|---|---|---|
| **Per-IP поріг** | N невдалих спроб з одного IP за останні `failedAttemptsWindowDays` днів (за замовчуванням 1) — багаторівнева ескалація (3 → 30 хв, 5 → 3 год, 7 → 2 доби) | `levels`, `failedAttemptsWindowDays` |
| **Spray** | Один і той самий логін атакують з N різних IP по всьому інтернету за коротке вікно | `antiBrute.spray` |
| **Subnet+user spray** | Той самий логін атакують з N різних IP **всередині однієї /24-підмережі** — ловить «low-and-slow» перебір (1-2 спроби на IP), який не спіймати одним per-IP порогом | `antiBrute.subnetUserSpray` |
| **IP abuse** | З одного IP перебирають N різних логінів | `antiBrute.ipAbuse` |
| **Subnet-ескалація** | Якщо з однієї /24 вже забанено N різних IP — банується вся підмережа (з перевіркою, що там немає активної легітимної RDP-сесії чи whitelisted-адреси) | `antiBrute.subnet` |
| **Recurrence** | Повторні бани одного IP збільшують час наступного блокування | `antiBrute.recurrence` |

Локальні/приватні діапазони (10.x, 172.16–31.x, 192.168.x, loopback) і явний whitelist (`whiteList.log`) ніколи не блокуються.

Лічильник спроб і активні бани коректно обнуляються як при закінченні терміну, так і при ручному розбані (з Monitor або Telegram) — включно з випадком, коли кілька різних співробітників сидять за одним «сірим» IP офісу і іноді помиляються в паролі.

### Застосування блокування

Реальне блокування — через 16 правил Windows Firewall (`RDP_BLOCK_0` … `RDP_BLOCK_15`, шардинг за IP), а не одне гігантське правило: так оновлення одного бану не вимагає переписувати список із тисяч чужих адрес і не може «завалити» синхронізацію для всіх інших. Джерело істини — файл `block_list.log`; служба перечитує його при будь-якій зміні і раз на 15 хвилин примусово звіряє фактичний стан firewall із цим файлом (самовідновлення після ручного втручання ззовні).

### Telegram-бот

Вбудований бот (long polling, без вебхуків) з двома ролями:

- **admin** — повний доступ: статуси, ручний бан/розбан, зупинка служби/монітора, керування whitelist.
- **limited** — лише кнопка «Розблокуй мене» (self-unban заздалегідь сконфігурованого IP, `telegram.selfUnbanIp`), для непривілейованих користувачів.

Ключові команди: `/status`, `/status all`, `/thresholds`, `/ban <ip> <тривалість>`, `/unban <ip>`, `/service start|stop|status`, `/monitor start|stop`, `/here` (геолокація через HTTP-пробник).

## Встановлення

Готова збірка (self-contained, .NET встановлювати окремо не потрібно) — у [`Install/`](Install/):

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
cd Install
.\install.ps1 -StartMonitor
```

Подробиці — в [Install/README.md](Install/README.md). Якщо волієте зібрати з вихідників самі — там же є команди `dotnet publish`.

Monitor вимагає запуску з правами адміністратора (це прописано в його маніфесті) — без цього він не зможе читати/писати конфігурацію та логи служби.

## Налаштування

Конфігурація лежить у `C:\ProgramData\RDPSecurityService\config.json`. Файл зберігається **зашифрованим** (Windows DPAPI, machine-scope) — вручну його не редагують, усі зміни робляться через Monitor (вкладка Settings/Telegram) або через Telegram-команди адміністратора. Схема полів — у [`WinService/config.example.json`](WinService/config.example.json) (цей файл — просто довідковий шаблон у відкритому вигляді, не те, що реально читає служба).

Основні поля:

- `port` — порт RDP, який слухає служба для кореляції з подіями входу.
- `failedAttemptsWindowDays` — скільки днів «живе» одна невдала спроба в per-IP лічильнику.
- `levels` — пороги ескалації блокування (спроби → хвилини бану).
- `telegram` — токен бота, ID чату адміністратора, список дозволених телефонів для limited-ролі, `selfUnbanIp`.
- `antiBrute` — увімкнення та параметри кожної з евристик вище.

## Обмеження

Це додатковий шар захисту поверх штатної гігієни, а не заміна їй:

- Не замінює NLA, складні паролі, MFA — вгадування пароля за 1 спробу жоден поріг не зупинить.
- Не захищає від атак з приватних/локальних діапазонів IP (by design) — нульовий захист від бокового переміщення всередині мережі.
- Атака з одночасною ротацією і IP, і логіна на кожну спробу (рідкісний, цільовий сценарій) обходить усі поточні евристики.

Рекомендована практика: RDP за VPN, NLA увімкнена, порт винесено з 3389 — цей сервіс як додатковий рубіж проти масового автоматичного сканування та скриптового брутфорсу.
